# Review decisions

Use these examples when choosing between two plausible implementations. They record which solution the team kept in production projects. Recheck installed adapter and component capabilities in the target project.

## Form and dialog ownership

- **Search is a form.** In a booking app, the reviewer identified a hand-written copy of Form's submit and processing behavior. The merged GET Form submits named fields, keeps relevant search/table state and resets the page when filters change. Pagination still has its own navigation. In a webshop, providing typed filter defaults from the request also removed client-side fallbacks and an unnecessary remount.
- **Choose the dialog structure from the slots and events it needs.** A training portal's user drawer uses `:as="Form"` with scoped errors, a submit button and `disable-while-processing`. An older Drawer in another project needed an outer Form to expose the slots.

  The same portal's planning drawer originally used an explicit inner Form so its close handler could read `isDirty` and reset the form outside the slots. A follow-up tried `:as="Form"` with an adapter to expose the same state. The team kept the simpler inner Form while the discard prompt was needed. The portal later removed the prompt, restored `:as="Form"`, and set `persistent` to keep the drawer open on Escape and outside clicks. Cancel, the close button and successful saves still close it.
- **Editable data and submitting it can have distinct needs.** A reporting portal's report editor removed manual JSON snapshots. A `useForm` draft owns editable values and dirty tracking, the rendered Form submits and supplies errors/processing, and a stream tracks its own progress. A planning app gave its reorder interaction a dedicated form because schedule editing is an independent operation. When changing APIs, check disabled controls: the declarative form serializes successful named controls, while a programmatic form submits its data object.

## Response contracts

- **A mutation that updates the displayed page.** The training portal replaced a standalone attendance request returning 204 and a client-side queue/rollback with a native optimistic visit, a redirect back and a partial refresh of server-owned attendance. For success messages, review asked it to reuse the central toast other projects already used. The merged controllers flash to the session and the layout consumes the middleware's `flash.success`.
- **A result needed once.** A measurement app starts a report job with a Form, redirects and sends the job ID through native Inertia flash. The caller reads `page.flash` and then polls for the report. The webshop's footer instead uses a named newsletter error bag and an existing session-backed message. The newsletter appears across pages. Feedback for a standalone Craft contact form was removed from shared middleware and stayed with the form's JSON response.
- **A deliberate same-page response.** A logistics portal's final rate preview computes rows without persisting them. It renders the current page with `indexedRows`, which the Form applies to its editable draft. A redirect/flash proposal appeared in the earlier PR. The merged successor is the reference. The webshop's cart is a different exception: the mutation already has expensive Commerce data, and a guarded direct response avoids reading it again. It preserves the expected page component, canonical URL and redirect fallback.

## Shared data and partial visits

- **Scope and freshness are separate decisions.** The logistics portal uses page-level once props for report options and a middleware once prop for currencies used across screens. The reporting portal's portal-scope flag must be recalculated and explicitly becomes false after leaving a scoped route. The Laravel template keeps existing Jetstream user data when adding permissions to the shared auth contract.
- **Choose a consumer and a loading boundary.** The training portal's page-specific evaluation drawer reads its event through `usePage()` and receives the selected participant from its parent. The webshop explicitly gives ordinary content components props and allows site-wide layout components to read shared data. The planning app puts the small, permission-scoped employee list on the page but keeps a separate search request for library items. The reporting portal chose an optional lookup prop when opening or searching a picker should trigger the query.
- **Refresh the entire affected set.** A rate-sheet change in the logistics portal must refresh both the sheet and its options. The webshop's filters must reset previously merged product pages. Its installed Link did not forward the reset option, so the fix moved that visit to the router. Use the installed adapter's visit options and request helpers when handling partial responses.

For v3 API behavior, see the official [forms](https://inertiajs.com/docs/v3/the-basics/forms), [redirects](https://inertiajs.com/docs/v3/the-basics/redirects), [flash](https://inertiajs.com/docs/v3/data-props/flash-data), [shared data](https://inertiajs.com/docs/v3/data-props/shared-data) and [partial reload](https://inertiajs.com/docs/v3/data-props/partial-reloads) documentation. Use the matching major for older projects.

# Submit a new Inertia decision

The source of truth is `resources/boost/skills/inertia-best-practices/` in [robuust/boost](https://github.com/robuust/boost). The copies in a project's `.agents/skills` and `.claude/skills` are generated by `vendor/bin/robuust-agents sync`; never edit them. Carry out this workflow in the implementation task once the developer chooses an uncovered approach. An explicit local-only or review-only request takes precedence over publication.

1. Fetch the current default branch of the shared repository and read the relevant section. Check open PRs for the same decision. If the rule has already landed and covers the case, use it. If an open PR already proposes the same rule, report its URL. When refining an earlier submission of your own, resume its existing branch and PR.
2. For a new decision, prepare a clean feature branch from the current default branch in the shared repository, separate from the application's changes. If the relevant skill section exists only in an open PR, base the follow-up on that PR's branch and identify the dependency. Write the rule where a future agent will look for it. State the condition, the chosen behavior and any reason or exception that changes the choice. Keep project- or version-specific decisions scoped. Update the existing rule when the developer revises it.
3. Validate the skill frontmatter, local links and the complete proposed diff. For a guidance-only decision with no outstanding behavioral check, passing these checks settles the test decision for this submission. Record behavioral tests as N/A and proceed without an additional test-waiver prompt. If a specific behavioral check is needed or executable code changes, follow the usual test authorization rules. Keep customer data, credentials and private chat transcripts out of the contribution.
4. The developer's choice triggers a PR for the skill change. Follow the repository's PR template and the `robuust:github-submit-review` workflow skill when it is installed. Commit and push the scoped branch and open the PR for review in the same task, without asking again for permission to publish the skill update. Leave the PR open for review, with auto-merge off. Delivery of application code has its own authorization.
5. Read back the PR and verify the destination, head and proposed rule. Report the URL to the developer. After an interruption or ambiguous response, check the remote branch and PR before retrying. If publication is blocked, retain the prepared change when possible and report the specific blocker and any remaining publication step.
